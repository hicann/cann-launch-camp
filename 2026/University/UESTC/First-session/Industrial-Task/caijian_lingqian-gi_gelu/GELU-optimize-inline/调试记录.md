## v19：exact erf GELU 重写（Horner 多项式）与编译错误修复

### 动机
v13 tanh 公式虽然通过，但：
- tanh GELU 是近似公式（PyTorch 官方近似），非数学严格 erf GELU
- 平台新增测试点6（更大数据量），对精度和性能提出更高要求

改用 **exact erf GELU**：`GELU(x) = 0.5 * x * (1 + erf(x/√2))`，其中 `erf(z) = z * P(z²)`，P 为 degree-10 minimax 多项式（绝对误差 < 3e-5 on |x| ≤ 4.95）。仅用 Muls/Mul/Adds 三种指令，避免 Reciprocal（精度低）和 Exp（开销大）。

### v19（exact erf）编译错误

| 版本 | 测试点1 | 测试点2 | 测试点3 | 测试点4 | 测试点5 | 测试点6 | 备注 |
|------|:------:|:------:|:------:|:------:|:------:|:------:|------|
| v19（exact erf） | CE | CE | CE | CE | CE | CE | 6/6 全部编译错误 |

### 编译错误根因分析

#### 根因 1：`ComputeFp32` 输出张量的 `const` 修饰

`ComputeFp32` 函数签名（第183-187行）：

```cpp
__aicore__ inline void ComputeFp32(const AscendC::LocalTensor<float> &x,   // ✅ x 只读
                                   const AscendC::LocalTensor<float> &bufA, // ❌ 被 Muls/Mul 写入
                                   const AscendC::LocalTensor<float> &bufB, // ❌ 被 Muls/Mul/Adds 写入
                                   const AscendC::LocalTensor<float> &y,    // ❌ 被 Muls/Mul/Adds 写入
                                   uint32_t count) {
    AscendC::Muls(bufA, x, INV_SQRT2, count);  // ❌ 向 const 引用写入
    AscendC::Mul(bufB, bufA, bufA, count);       // ❌ 向 const 引用写入
    // ... 后续 20+ 行全部向 const 参数写入
}
```

AscendC API 的 `Muls(dst, src, scalar, count)` / `Mul(dst, src0, src1, count)` / `Adds(dst, src, scalar, count)` 要求 `dst` 为非 const 引用。编译器在语义检查阶段拒绝将 const 对象绑定到非 const 引用参数，导致所有调用点编译失败。

#### 根因 2：`Muls(y, ERF_C10, count)` 三参数 broadcast 形式

```cpp
// Horner 多项式初始化：y = C10（最高次系数，广播到所有元素）
AscendC::Muls(y, ERF_C10, count);  // ❌ 3 参数形式 (dst, scalar, count)
```

同目录 `gelu_demo.asc` 中所有 `Muls` 调用均为 4 参数形式 `Muls(dst, src, scalar, count)`（即 `dst = src * scalar`）。3 参数形式 `Muls(dst, scalar, count)`（即 `dst = scalar`，无 src）在竞赛平台的 CANN 版本中可能不存在或签名不同，存在兼容性风险。

### 修复方案（v19-fix）

#### 修复 1：移除 `const` 修饰

```cpp
// 修改前
__aicore__ inline void ComputeFp32(const AscendC::LocalTensor<float> &x,
                                   const AscendC::LocalTensor<float> &bufA,
                                   const AscendC::LocalTensor<float> &bufB,
                                   const AscendC::LocalTensor<float> &y, ...)
// 修改后
__aicore__ inline void ComputeFp32(const AscendC::LocalTensor<float> &x,
                                   AscendC::LocalTensor<float> &bufA,
                                   AscendC::LocalTensor<float> &bufB,
                                   AscendC::LocalTensor<float> &y, ...)
```

仅 `x` 保留 `const`（只读输入），`bufA`/`bufB`/`y` 全部去 `const`。

#### 修复 2：3 参数 → 4 参数安全写法

```cpp
// 修改前
AscendC::Muls(y, ERF_C10, count);  // 3参数，兼容性风险

// 修改后
AscendC::Muls(bufA, x, 0.0f, count);  // bufA = 0 (x * 0.0)
AscendC::Adds(y, bufA, ERF_C10, count); // y = 0 + C10 = C10
```

**安全性说明**：
- `bufA` 在 Step1 存储 `z = x/√2`，但 Horner 阶段（Step2 之后）只需要 `z²`（存储在 `bufB`），`z` 本身不再被读取
- 第211行 `Muls(bufB, x, INV_SQRT2, count)` 在 Horner 结束后重新计算 `z` 到 `bufB`
- 因此覆盖 `bufA` 为零缓冲是安全的，不会破坏后续计算

### 经验教训

1. **`const` 在向量指令输出参数上是硬错误**：AscendC 的 `Muls`/`Mul`/`Adds` 第一个参数 `dst` 必须是非 const 左值引用。C++ 编译器无法隐式去除 const，导致全部调用点报错。

2. **API 兼容性不可假设**：demo 文件全部使用 4 参数 `Muls(dst, src, scalar, count)`，说明竞赛平台 CANN 版本可能不支持 3 参数 broadcast 重载。必须严格遵循 demo 文件的 API 使用模式。

3. **6 测例全 CE 的典型特征**：所有测例同一错误、错误占比 100%，说明是编译器层面的问题（而非运行时逻辑错误）。优先检查函数签名和 API 调用兼容性。

### v21：A-S 风格 erf（fp32） + Horner 降阶（fp16）

**双路径策略**：

| 路径 | erf 实现 | 指令数 | 新增 API |

v21 初版 fp32 路径持续 **~77% WA**（测试点 2/3/5/6），fp16 全部 Pass。以下为完整排查过程：

**全部死码测试通过！** 说明任何单条指令都不产生污染。

#### 恢复完整 A-S 并验证

提交 `10380a7`：恢复 `ComputeFp32Direct → ComputeFp32AS`，结果 **仍 77% WA**。

**关键洞察**：死码测试的盲区 — Horner8 覆盖了 A-S 的输出，**死码测试只验证"不污染"，无法验证"正确计算"**。Add dst=src0 可能产生错误结果，但 Horner8 覆盖后测试通过。

#### 修复 Add 别名（最终根因）

将 GELU 终段的 `Add` 从 dst=src0 改为全独立操作数：

| | 修改前（6 指令） | 修改后（4 指令） |
|---|---|---|
| 1 | `Abs(bufB, x)` → \|x\| | `Abs(bufB, x)` → \|x\| |
| 2 | `Mul(bufA, bufB, bufA)` → \|x\|·erf | `Mul(bufA, bufB, bufA)` → \|x\|·erf |
| 3 | `Muls(bufB, x, 0.5f)` → 0.5·x | `Add(bufB, x, bufA)` → x+\|x\|·erf |
| 4 | `Muls(bufA, bufA, 0.5f)` → 0.5·\|x\|·erf | `Muls(y, bufB, 0.5f)` → GELU |
| 5 | `Add(bufB, bufB, bufA)` **dst=src0** ⚠️ | — |
| 6 | `Muls(y, bufB, 1.0f)` → GELU | — |

新 Add: `Add(bufB, x, bufA)` — bufB(VECCALC) ≠ x(VECIN) ≠ bufA(VECCALC)，三个操作数完全独立。

**结果（提交 `dfd7cc4`）：6/6 Pass！** A-S 路径终于正确。

### 经验教训

1. **死码测试的盲区**：死码测试只能验证"指令执行不污染后续状态"，无法验证"指令计算是否正确"。必须让计算结果流向最终输出才能验证正确性。

2. **Add dst=src0 别名在此平台产生产生错误结果**：虽然 Add 无别名、Add dst=src0 死码均通过，但 Add dst=src0 真实结果流向输出时出 77% WA。Add、Mul 对别名容忍度不同。

3. **硬件加速不一定等于更快**：Exp/Reciprocal 是硬件指令但在此平台执行周期长，纯 Mul/Adds 多项式反而更快。Demo 的风格不代表最优。

4. **A-S 与 Horner buffer 约束不同**：A-S 需要 y（TQue）暂存 exp 中间值（需 VECOUT 读回），Horner 的 y 仅作累加器。fp16 的 y=BufA 别名使 A-S 不可用，但 Horner 的 dst=src1 别名在此平台安全。

5. **隔离测试是定位未知问题的有效手段**：7 步递进从框架→Abs/Exp→Reciprocal→Horner→Add→VECOUT→全流程，每步仅增加 1-2 条新指令。最终发现死码测试盲区后，对比"全流程死码+Horner8"与"纯 A-S"锁定 Add 结果正确性问题。

## 最终根因总结（三个层级）

### 层级 1：TPosition 枚举值错误
`static_cast<TPosition>(1)` = **A1**（矩阵缓冲区），不是 VECOUT(10)。
TQue 输出数据被路由到完全错误的硬件通道。

### 层级 2：CopyIn/CopyOut API 混用
CopyIn 用 DataCopyPad，CopyOut 违规用 DataCopy。官方要求必须统一。

### 层级 3：erf 公式精度不足
AscendC Reciprocal+Exp 精度约 1e-4，22 步累积后超标。切换 tanh 公式（9 步，硬件 Tanh）解决。

## v23：Tanh 近似探索（cubic → sigmoid → 5th-order predistorted）

### 动机

v22-final Horner8 6/6 Pass，但 test6 117μs 仍是瓶颈。Tanh 硬件指令可能更快。探索三种 Tanh/Sigmoid 近似。

### v23a：Cubic Tanh（10 ops，接近最优速度）

**公式**：GELU(x) ≈ 0.5x·(1 + tanh(√(2/π)·(x + 0.044715·x³)))

**流程**（10 条指令）：
```
Mul: x² → Muls: 0.044715·x² → Mul: 0.044715·x³ (dst=src1 ✓)
Add: x + 0.044715x³ (all-distinct ✓)
Muls: √(2/π)·z → Tanh → Adds: 1+tanh → Muls: 0.5x → Mul: GELU → Muls: output
```

**结果**：5% WA（测试点 2/3/5/6），错误集中在最坏误差 ~4e-3 的元素。常数精度已达 float32 边界，无法进一步改善。

**教训**：Cubic tanh 的近似误差 ~4-5e-5，部分元素刚好超过 1e-4 门限。

### v23b：Sigmoid（6 ops，理论更快但精度不够）

**公式**：GELU(x) ≈ x / (1 + exp(-1.702·x))

**流程**（6 条指令）：
```
Muls: -1.702x → Exp → Adds: 1+exp → Reciprocal → Mul: x·σ (dst=src1 ✓) → Muls: output
```

**结果**：0/6 Pass（1: 59% WA, 2-6: 93% WA），速度极快（test6=48μs，接近最优 48.7μs）但精度太差。

**根因**：Sigmoid 近似误差 ~3e-4（10 倍于 cubic tanh）。Exp+Reciprocal 在此平台输出值不准（A-S 调试已验证）。

**教训**：Exp+Reciprocal 不可用于数值关键路径。速度虽好但精度不达标。

### v23c：5th-order Predistorted Tanh（14 ops，最终方案）

**关键发现**：Cubic tanh 5% WA 不够，Sigmoid 精度太差。需中间方案——精度好于 cubic，速度快于 Horner。

**公式**：z = √(2/π)·x + K₃·x³ + K₅·x⁵，K₃/K₅ 已预乘 √(2/π)
```
GELU(x) ≈ 0.5x·(1 + tanh(z))
```

**因式分解（消 Add 别名）**：
```
poly = x³·(K₃ + K₅·x²)    ← 无 Add，仅 Mul/Adds/Muls
z = √(2/π)·x + poly
```

**常量**：
```
K₃ = 0.035677f    (= √(2/π) × 0.044715)
K₅ = 0.000521f    (= √(2/π) × 0.000654)
TANH_A = 0.797884583f
```

**流程**（14 条指令）：
```
Mul: x² → Muls: K₅·x² → Adds: K₃+K₅·x² → Mul: x²(重建) → Mul: x³(dst=src1 ✓)
Mul: poly (dst=src1 ✓) → Muls: √(2/π)·x → Muls: poly→VECOUT → Add: z (all-distinct ✓)
Tanh → Adds: 1+tanh → Muls: 0.5x → Mul: GELU (dst=src1 ✓) → Muls: output
```

**结果**：6/6 Pass！

### v23 经验教训

1. **Tanh 是此平台最可靠的硬件加速函数**：比纯 Mul/Adds 多项式快，比 Exp/Reciprocal 准。

2. **因式分解消 Add 是安全模式**：`x³·(K₃+K₅·x²)` 将 2 项多项式合并为纯 Mul/Adds，完全消去 Add 别名风险。Add dst=src0 在此平台产生错误结果，必须避免。

3. **DMA-Bound 限制收益**：14 ops vs 24 ops 仅改善 ~6%，计算被 DMA 完全隐藏。进一步优化指令数意义不大。

4. **预缩放常量节省运算**：K₃=√(2/π)×0.044715 在编译期计算，省去运行时 `Muls<K₃_raw>` + `Muls<√(2/π)>` 两条指令。

5. **5% → 0%：一个小系数的力量**：Cubic tanh 误差刚好压线（5% WA），添加 0.000521·x⁵ 项将最坏误差从 ~4e-5 压至 ~2e-5，刚好过 1e-4 门限。

## v24-v27：DMA/Tiling 深度优化与 ops-nn 学习

### v24：TQue depth=1（CE）

**动机**：TQue 深度 2→1，UB B/elem 减少，tile 增加。

**结果**：CE——竞赛平台最低 TQue 深度为 2。

### v25：VECCALC-only DMA（WA→CE）

**动机**：ops-nn 的 `index_fill_d` 使用 VECCALC 直接 DMA，tile 可达 12,000+。

**结果**：WA 99%（DataCopy 不兼容）→ CE（DataCopyPad 仅支持 GM↔VECIN/VECOUT）。

**根因**：AscendC 文档明确 TBuf (VECCALC) 不支持 GM↔UB DMA。TQue 是唯一通道。

### ops-nn 源码分析

ops-nn 使用**混合架构**：
```
DMA:   TQue + DataCopyPad（同我们）
计算:  MicroAPI::RegTensor + __simd_vf__（寄存器，零TBuf）
```
关键：寄存器计算不占 UB 空间 → tile 可达 12,288（+52%）。

### v26：MicroAPI 尝试（CE）

**结果**：CE——`__simd_vf__`、`MicroAPI::*` 属于 SIMD C API 层，竞赛平台不支持。

### v27：11 ops 指令优化（6/6 Pass，性能回退）

**修改**：
1. `Mul(y, bufB, bufA)` 直写 VECOUT（消 Muls 拷贝）
2. `Add(bufA, bufB, bufA)` dst=src1（消 poly 拷贝）

**结果**：test6 106→138μs (+30%)。功能正确（6/6 Pass）但性能恶化。

**根因**：VECOUT 直写触发 TQue 队列同步延迟。原有 VECCALC→Muls→VECOUT 将计算与输出解耦。
