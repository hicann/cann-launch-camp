## 发现并修复的问题

### 问题 1：DataCopy 非 32 字节对齐

**发现工具**: `ascend-code-reviewer` — DataCopy 对齐检查

**问题描述**:

在 CPU/Kernel 分块循环中，末核最后一轮迭代的数据量 `count` 可能不是 32 字节对齐的。AscendC 的 `DataCopyPad` 要求搬运长度 `blockLen` 为 32 字节的整数倍，否则会导致硬件异常或数据错乱。

**触发场景**:

```
float32, totalLength = 31, numCores = 24
  → blockLength = ceil(31/24) = 2 → 向上32字节对齐 → 8
  → usedCores = ceil(31/8) = 4
  → 核3: offset=24, blockLength_ = 7 (31-24)
  → 最后一轮 count = 7
  → blockLen = 7 * 4 = 28 字节  ← ❌ 非32字节对齐
```

**修复方案**：

```cpp
// 修复前
uint32_t count = (i + ubLength_ <= blockLength_) ? ubLength_ : (blockLength_ - i);
uint32_t blockLen = static_cast<uint32_t>(count * sizeof(T));
DataCopyPad(xLocal, inputGM_[i], copyParams, padParams);  // blockLen 可能非32B对齐

// 修复后
uint32_t count = (i + ubLength_ <= blockLength_) ? ubLength_ : (blockLength_ - i);
uint32_t blockLen = static_cast<uint32_t>(count * sizeof(T));
constexpr uint32_t ALIGN_32 = 32;
uint32_t blockLenAligned = blockLen & ~(ALIGN_32 - 1);  // 向下32字节对齐
if (blockLenAligned == 0) continue;  // 不足32字节则跳过
uint32_t countAligned = blockLenAligned / sizeof(T);
// 使用 countAligned 进行 DataCopy
```

**涉及文件**: `op_kernel/gelu.cpp` — `Process()` 方法

### 问题 2：float16 纯半精度计算精度不足

**发现工具**: `precision-verifier` — float16 精度检查

**问题描述**:

赛题要求 float16 模式相对误差 < 1e-3、绝对误差 < 1e-3。但 float16 的尾数精度仅约 10 位二进制（~3.5 位十进制），而 GELU 的 erf 近似包含 11 步链式运算（Abs → Muls → Mul → Exp → ... → Add → Muls），每一步都会累积量化误差。

主要风险点：

| 运算步骤 | float16 精度风险 |
|----------|-----------------|
| 常量精度损失 | ERF_A1~ERF_A5 等 float32 字面量截断为 float16 |
| Horner 多项式 | 5 次乘法 + 4 次加法在 float16 下累积误差 |
| exp(-a²) | 浮点下溢导致 erf 计算失败 |
| 最终缩放 | 0.5 乘法的舍入误差 |

**修复方案**：

引入混合精度计算路径——输入/输出保持 float16，中间计算提升到 float32：

```
float16 I/O
    │
    ▼
Cast(half → float)    ← 精度提升
    │
    ▼
全 float32 计算        ← 11 步链式运算均在 float32 下进行
(Abs → Muls → Mul → Exp → ... → Add → Muls)
    │
    ▼
Cast(float → half)    ← 仅最后一步降精度
    │
    ▼
float16 输出
```

同时利用 `if constexpr` 编译期分发，float32 路径保持零开销：

```cpp
__aicore__ inline void Compute(const LocalTensor<T> &xLocal, uint32_t count) {
    if constexpr (sizeof(T) == 2) {
        // float16：混合精度
        ComputeFp16(xLocal, count);
    } else {
        // float32：直接计算
        ComputeFp32Direct(xLocal, count);
    }
}
```

**涉及文件**: `op_kernel/gelu.cpp` — `Compute()` 方法及 `ComputeFp16()` / `ComputeFp32()` / `ComputeFp32Direct()` 函数族

### 问题 3：float16 混合精度路径 Buffer 大小不足

**发现工具**: `ascend-code-reviewer` — UB 内存管理检查

**问题描述**:

在引入混合精度计算后，float16 模式下临时 buffer（`tmpBuf1_`~`tmpBuf4_`）的分配大小仍为 `ubLength * sizeof(half)`。但混合精度路径以 `float` 视图（`.Get<float>()`）访问这些 buffer，导致访问越界——实际可用 float 元素数只有需求的一半。

```
修复前分配：
  tmpBuf1_.InitBuffer(pipe_, ubLength * sizeof(half))   // ubLength * 2 bytes
  tmpBuf1_.Get<float>()  → 只有 ubLength/2 个 float    // ❌ 不够用

修复后分配：
  tmpBuf1_.InitBuffer(pipe_, ubLength * sizeof(float))  // ubLength * 4 bytes
  tmpBuf1_.Get<float>()  → 有 ubLength 个 float        // ✅ 正确
```

UB 容量校验（Ascend 910B, UB = 192KB）：

| 场景 | 分配内容 | 总量 | UB 占比 |
|------|---------|:----:|:------:|
| float32 | 输入(4B) + 输出(4B) + 4×临时(4B) = 24B/元素 | ~173KB | 90% ✅ |
| float16 | 输入(2B) + 输出(2B) + 4×临时(4B) = 20B/元素 | ~144KB | 75% ✅ |

**涉及文件**: `op_kernel/gelu.cpp` — `Init()` 方法
