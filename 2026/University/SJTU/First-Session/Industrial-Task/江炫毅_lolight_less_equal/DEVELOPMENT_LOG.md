## 一、赛题目标

LessEqual 算子对两个输入张量执行逐元素比较：

```text
y[i] = (x1[i] <= x2[i])
```

核心要求：

- 支持 `float16`、`float32`、`int32`、`int8`。
- 输出类型固定为 `bool`。
- 支持 NumPy/TensorFlow 广播语义。
- 支持非 32 字节对齐的尾块。
- 比较结果必须完全准确。
- 在 Ascend 910B 上尽量缩短执行时间。

这道题表面是简单比较，实际同时涉及 Host 注册、Tiling、模板实例化、GM/UB 搬运、广播索引、向量 mask 展开、多核切分和评测环境适配。

## 二、总体历程

整个过程可分为八个阶段：

1. 建立能够编译的算子骨架。
2. 解决 Host 注册与 Tiling 失败。
3. 建立无向量指令的正确性基线。
4. 恢复向量 Compare 并处理四种数据类型。
5. 修复广播与 INT8 Wrong Answer。
6. 从 17 分版本提升到 61 分版本。
7. 合并紧凑广播架构，将成绩提升到 65 分。
8. 按数据类型设计多核策略达到 70.37 分、第 5，并通过广播校验改进与复测达到 77.69 分、第 2。

## 三、第一阶段：先让工程编译

### 3.1 Host 模板宏错误

早期提交曾出现：

```text
ASCENDC_TPL_ARGS_DECL: expected constructor, destructor, or type conversion
ASCENDC_TPL_SEL: expected constructor, destructor, or type conversion
ASCENDC_TPL_SEL_PARAM was not declared in this scope
```

典型提交号包括 `88475`。

根因不是 Kernel 算法，而是 Host 编译阶段直接包含了 Kernel 模板配置头，但模板宏或头文件组合不符合 CANN 8.5 的 Host 编译环境。

这一阶段得到的第一条原则：

> 构建日志要从第一条真实错误开始看，后面的 CMake、make 和 Python traceback 通常只是连锁反应。

### 3.2 ACLNN Workspace 查询失败

多轮提交出现：

```text
aclnnLessEqualGetWorkspaceSize(...) failed
ret=561002
```

这类错误发生在真正启动 Kernel 之前，说明问题位于：

- 算子注册信息；
- 输入输出类型或形状推导；
- Tiling 返回状态；
- 模板选择；
- Host 生成的算子元信息。

它不是 NPU 计算结果错误，也不是性能问题。继续优化 Kernel 对这种错误没有意义。

### 3.3 经验

这一阶段最大的收获是建立故障分层：

```text
Host 编译
→ 算子注册与代码生成
→ Kernel 入口识别
→ Kernel 编译
→ Workspace/Tiling
→ 设备运行
→ 正确性比较
→ 性能计时
```

每一层只解决本层第一条错误，避免同时改动多个无关文件。

## 四、第二阶段：正确性基线

### 4.1 毕昇编译器与 Compare

早期尝试为不同类型增加 `Compare` 特化，但毕昇编译器的检查行为与标准 C++ 模板直觉并不完全一致。

尝试过的隔离方式包括：

- 模板全特化；
- 函数重载；
- `if constexpr`；
- 先 Cast 到 float 再 Compare；
- 在独立头文件中选择模板参数。

这些方案中一部分会在未预期的类型上触发向量 API 合法性检查，一部分会遇到签名不匹配或 UB 容量问题。

### 4.2 88588：零 Compare 标量版

为了先证明 Host、广播、搬运和输出格式正确，形成了全文件不使用 `Compare` 的标量版本。

结果：

- `5 / 5 Pass`
- 正确性基线建立成功
- 性能约 17 分
- 大测试点接近 `459 us`

这一版虽然慢，但价值很高：它把问题从“功能是否正确”收敛为“如何安全向量化”。

### 4.3 经验

> 高性能优化前必须保留一个绝对可靠的正确性基线。没有基线，每次 Wrong Answer 都无法判断是新优化引入，还是旧逻辑本来就错。

## 五、第三阶段：第一次向量化突破

### 5.1 88498：早期 5/5 版本

`88498` 已经能够 5/5 通过，但性能仍较低，排行榜得分约 17 分。

主要特征：

- 主模板与 half 比较逻辑已经可用；
- 广播仍存在大量逐元素索引和标量访问；
- INT8、INT32 路径没有形成稳定的全向量方案；
- UB、核心数和 Tile 长度偏保守。

### 5.2 88608：性能飞跃但 3/5

`88608` 引入了两个关键思想：

- 使用 `Duplicate` 代替逐元素广播填充；
- 从末维开始寻找连续区间，批量搬运广播数据。

性能显著提升，但结果只有 `3 / 5 Pass`：

- 测试点 2 Wrong Answer，错误占比约 `0.73%`；
- 测试点 5 Wrong Answer，错误占比约 `50.06%`。

当时重点怀疑：

- INT8 packed Duplicate 的奇数长度尾部；
- INT32/INT8 缺少合适的向量特化；
- 广播连续段判断与真实 stride 不一致。

### 5.3 从 Wrong Answer 学到的事

错误占比本身是诊断信息：

- 极小比例错误通常指向尾块、非对齐或边界；
- 接近 50% 往往指向比较方向、广播索引或大段地址映射错误；
- 100% 常见于输出格式、Kernel 未执行或整体地址错误。

## 七、第五阶段：大量单变量实验

这一阶段消耗了大量提交次数。目的不是堆代码，而是寻找真正影响五个测试点的变量。

### 7.1 INT8 packed 标量特化

尝试用更宽的打包 Duplicate 优化 INT8。

结果示例：

```text
4.06 / 5.20 / 13.92 / 6.00 / 20.74 us
```

结论：

- 测试点 4 略有改善；
- 测试点 2、5 回退；
- 不是整体最优方向。

### 7.2 降低每核最小工作量

曾将非广播路径的目标工作量从 8192 或 2048 降到更小值，希望使用更多 AIV 核。

结果出现：

- 测试点 3 TLE；
- 或者虽然 5/5，但整体时间更差；
- 核心启动和同步成本超过计算收益。

结论：

> 核数不是越多越快。不同数据类型、张量大小和执行路径需要不同的核心数量。

### 7.3 全核 INT8 标量路径

只对同形状 INT8 使用 32 元素对齐的全核分区。

结果：

```text
3.90 / 5.30 / 16.06 / 3.48 / 20.78 us
```

测试点 4 从约 `6.64 us` 降到 `3.48 us`，证明：

- 测试点 4 的主要瓶颈是核心利用率；
- 32 元素边界分核是有效变量；
- 其他测试点不应被同一策略强行改变。

### 7.4 FAST_INT8 独立 Tiling Key

尝试新增布尔模板参数，把快速 INT8 Kernel 与其他类型隔离：

- INT8 Cast 到 half；
- half Compare；
- mask 展开；
- 全核分区。

结果约为：

```text
4.00 / 5.34 / 15.48 / 3.62 / 20.50 us
```

结论：

- 正确性保持 5/5；
- 转换与 mask 后处理抵消了部分向量收益；
- 新模板键增加了复杂度，却没有带来足够分数。

### 7.5 单变量实验的价值

这些版本多数没有成为最终代码，但它们回答了关键问题：

- 测试点 4 需要更积极的多核调度；
- INT8 转 half 并不自动等于更快；
- 模板隔离有编译与二进制成本；
- 对所有类型统一满核会拖慢部分场景；
- 广播和同形状路径必须分开优化。

## 八、第六阶段：分析紧凑版本架构

开发过程中审阅了一份更紧凑的实现，重点借鉴其通用硬件思想，而不是直接复制代码：

- 同形状快速路径；
- 广播按行处理；
- 行状态递增；
- 全类型向量计算；
- 深度为 2 的输入输出队列；
- Min/Max 与 Compare 的等价变换。

同时发现了不能直接照搬的问题：

- 连续维度合并时错误覆盖内层 stride；
- Tile 按原始长度分配，却按向上对齐长度执行；
- mask 字节数存在向下取整风险；
- 非法广播没有严格拒绝；
- 所谓双缓冲仍是顺序 CopyIn、Compute、CopyOut，并未必形成真正跨 Tile 重叠。

这一阶段形成了重要边界：

> 可以学习公开的硬件优化思想，但最终提交必须有独立实现、清晰来源和可解释的技术决策。

## 九、第七阶段：89552，广播路径突破

### 9.1 Combined 架构

`89552` 形成了新的紧凑组合：

- Host 将同形状和广播拆成两种模式；
- 广播维度压缩为行与末维；
- Kernel 使用 `InitRowState` 计算首行偏移；
- 使用 `AdvanceRowState` 增量更新下一行；
- 避免对每个输出元素重复做完整的多维除法和取模；
- 四种数据类型全部使用向量路径；
- scalar 广播使用 Duplicate。

### 9.2 成绩

关键结果：

```text
3.92 / 5.30 / 10.64 / 4.24 / 17.74 us
```

汇总：

- `5 / 5 Pass`
- `65.60` 分
- 排名第 `8`
- 测试点 3 达到 `10.64 us`，一度快于排行榜当时最优值

这是广播架构真正生效的证据。

### 9.3 为什么测试点 3 提升明显

旧实现每个 Tile 仍需要多维 stride 推导或通用广播判断；新实现把外层广播转换为连续行任务：

```text
首行坐标计算一次
→ 每完成一行递增状态
→ 末维批量搬运与向量比较
```

计算复杂度和分支数量都显著下降。

## 十、第八阶段：89827 的入口错误

一次提交出现：

```text
kernel entry `less_equal` not implement in `less_equal.cpp`
```

四个 dtype 实例全部失败。

Host 已经成功编译，因此根因不是 Tiling，也不是多核公式，而是提交包中的 Kernel 文件：

- 文件放错位置；
- 复制被截断；
- Host 内容误放到 Kernel 文件；
- 或全局入口函数缺失。

通过完整恢复 89552 Kernel，重新加入：

```cpp
template <typename DT_X1>
__global__ __aicore__ void less_equal(...)
```

问题解决。

这一轮再次证明：

> 多文件手工复制时，必须检查文件路径、入口函数和文件尾，不能只看代码主体。

## 十二、约 50 次提交中的主要失败类型

### 12.1 Compile Error

常见原因：

- Host 侧包含不兼容模板宏；
- Tiling Key 参数与 Kernel 模板参数不一致；
- Kernel 全局入口函数缺失；
- Ascend C API 类型或参数签名不匹配；
- 手工复制导致文件截断或路径放错。

处理方法：

1. 只看第一条真实编译错误；
2. 判断错误属于 Host 还是 Kernel；
3. 检查模板参数数量；
4. 检查全局入口；
5. 用上一版可编译文件做逐文件对比。

### 12.2 Runtime Error

常见表现：

```text
aclnnLessEqualGetWorkspaceSize failed, ret=561002
```

应优先检查：

- Host 注册；
- InferShape；
- InferDataType；
- Tiling 返回值；
- 数据类型模板选择；
- 输出形状与广播合法性。

### 12.3 Wrong Answer

主要来源：

- 广播 stride 计算错误；
- 连续维度错误合并；
- INT8 奇数尾块；
- mask 展开或输出类型错误；
- 非对齐尾块读写；
- 比较方向写反。

### 12.4 Time Limit Exceeded

主要来源：

- 标量 `GetValue/SetValue` 循环；
- 广播逐元素计算坐标；
- 核数过少；
- 或反过来，核数过多导致启动开销超过收益；
- Tile 太小导致循环与搬运次数增加。

### 12.5 分数回退

微秒级评测存在抖动。同一路径在不同时刻可能变化 1 到 3 微秒。

因此判断优化是否有效时采用：

- 看变化是否集中在预期测试点；
- 看幅度是否超过正常抖动；
- 看是否能够由代码路径解释；
- 不根据一次单点小幅提升立即重构全局。

## 十三、最终技术心得

### 13.1 正确性与性能要分层

先建立 5/5 标量基线，再逐步替换为向量路径。正确性没有稳定前，不讨论排行榜。

### 13.2 广播是主要架构问题

广播不能只看末维是否为 1。高维广播需要正确的：

- 右对齐维度；
- 输出 shape；
- 输入 stride；
- 连续段判断；
- 行状态更新；
- scalar 与 contiguous 两种搬运方式。

测试点 3 从约 278 us 到约 12 us，主要来自广播架构变化，而不是单条向量指令。

### 13.3 向量化不等于自动变快

INT8 Cast 到 half 后 Compare 在理论上向量化，但包含：

```text
Cast A
+ Cast B
+ Compare
+ Select
+ Cast output
```

固定开销可能抵消收益。必须用真实测试点验证。

### 13.4 核数必须按类型和规模选择

最终最重要的调度结论：

- `float16/int8` 更适合积极并行；
- `float32/int32` 在当前测试规模下需要控制核心数；
- 广播应按行分配，而不是简单按总元素切块。

### 13.5 UB 必须按实际向量长度计算

如果向量指令处理 `RoundUp(L)` 个元素，所有相关 UB 缓冲必须覆盖对齐后的长度，包括：

- 输入；
- 输出；
- mask；
- half 临时缓冲；
- int32 Min/Max 临时缓冲。

即使比赛测试通过，越界设计也不应直接作为生产实现。

### 13.6 Tiling Key 不是越多越好

独立模板实例可以消除运行时分支，但也会增加：

- Host/Kernel 参数一致性风险；
- 编译复杂度；
- 二进制体积；
- 入口生成问题。

能用一个稳定模板和 Tiling 数据表达的策略，不必强行增加模板键。

### 13.7 比赛版与 PR 版应分离

比赛版目标是 5/5 和性能得分；公开 PR 还必须考虑：

- 完整非法输入检查；
- 大张量 64 位偏移；
- UB 严格边界；
- 广播组合的系统测试；
- 代码来源与许可证；
- CLA、目录和文档规范。

70.37 版本是课题优化过程中的稳定里程碑。公开提交前继续补充标准广播合法性校验，并通过排行榜复测确认功能和性能未回退。

## 十四、协作心得

### 14.1 人与 AI 的分工

这次协作中：

- 人负责提交、观察排行榜、保留评测结果和决定是否继续冒险；
- AI 负责日志分层、源码审计、静态推演、分核公式验证、完整文件输出和技术复盘；
- 其他 AI 的建议作为交叉审查输入，不直接视为事实。

### 14.2 有效协作方式

最有效的循环是：

```text
提供完整源码或提交包
→ 提供完整第一条错误或五点结果
→ 一次只改变一个核心变量
→ 完整替换所有相关文件
→ 保存提交号、代码和成绩
```

### 14.3 无效协作方式

最容易浪费提交次数的行为：

- 同时修改 Host、Kernel、Tiling 和模板键；
- 只复制代码片段导致文件混用；
- 没有确认当前基线版本；
- 把评测抖动当成确定优化；
- 在没有编译证据时继续叠加补丁；
- 为了代码看起来更复杂而增加防御逻辑或模板层次。

## 十五、如果重新开始

如果重新做一次，建议采用以下顺序：

1. 第 1 到 3 次提交：完成 Host 注册、InferShape、Tiling 和空张量。
2. 第 4 到 6 次提交：建立四类型标量 5/5 基线。
3. 第 7 到 10 次提交：只优化同形状 float16/float32。
4. 第 11 到 15 次提交：加入 int32 等价向量比较与 INT8 路径。
5. 第 16 到 22 次提交：单独完成广播行状态机。
6. 第 23 到 28 次提交：验证非对齐尾块与 UB 对齐。
7. 第 29 到 35 次提交：对四类型分别扫描核心数。
8. 第 36 到 42 次提交：扫描 Tile 上限和广播每核行数。
9. 第 43 到 47 次提交：复测最优组合，排除评测抖动。
10. 第 48 到 50 次提交：冻结比赛版、准备文档和 PR 版。

这样可以减少无效组合实验，并确保最后几次提交用于复测，而不是修复文件混用。
