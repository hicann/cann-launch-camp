### 1.3 个人开发过程说明

本次实践围绕「A8W8 量化 matmul 自定义算子开发并接入 Qwen3-8B 推理」展开，按「需求分析 → 算子开发 → 单算子测试 → 算子接入模型」的主线推进。

**需求与方案阶段**：明确算子语义为 INT8×INT8 累加得 INT32（无 per-token 场景输出 INT32），以及在 per-channel scale + per-token scale 反量化下输出 BF16，目标是替换网络中的 `npu_quant_matmul`。据此确定「Cube 主算 + Vector 反量化」的架构，并区分两条执行路径。

**实现阶段**：先设计 `QmmCustomTilingData`（`TCubeTiling cubeTilingData` + `isPertoken` + `workspaceSize` + `sysWorkspaceSize` + `M/N/K` + `ringDepth`），再实现 host 侧 `CalcQmmTiling`：用 `MultiCoreMatmulTiling` 按 A=ND int8、B=NZ int8、C=ND int32 生成 tiling，并补充 NZ `singleCoreN` 32 对齐护栏。Kernel 侧实现两条路径：**Path1**（`isPertoken==0`）Cube-only 把 INT32 结果直写 `y`；**Path2**（`isPertoken!=0`）单次 `__mix__(1,2)` launch，AIC 逐 base-tile 把 INT32 `C` 写入 workspace 中间缓冲，AIV 按 `fp32(C)*scale*pertoken` 两段 fp32 乘 + `Cast(CAST_RINT)` 反量化输出 BF16，AIC/AIV 通过 CrossCore 标志位握手。

**测试与接入阶段**：算子编译通过后，先跑单算子精度与性能测试，再完成 `npu_quant_matmul → qmm_custom` 替换，跑通模型 prefill/decode 与 profiling，从 `kernel_details.csv` 确认自定义算子确实在网络中执行，最后恢复原始 W8A8 源码。

**问题定位与解决**：推进中主要关注三类问题——（1）系统 workspace 绑定语义：直接下发场景需在 kernel 内 `SetSysWorkspace` 绑定，否则 matmul 引擎拿不到 `GetSysWorkSpacePtr()`；（2）NZ 格式 N 向 32 对齐：`singleCoreN` 不满足 32 对齐时按对齐值重新生成 tiling；（3）AIC/AIV 之间的跨核数据可见性：AIC 写完中间结果后通过 `CrossCoreSetFlag` 通知 AIV 消费，保证数据先于标志位可见。精度、性能与模型接入三项验证均需留有可追溯数据。

## 三、方案说明

### 3.1 设计思路

**TilingData 设计**：`QmmCustomTilingData` 以 `TCubeTiling` 为核心，附加 `isPertoken` 区分输出类型（INT32 / BF16）、`sysWorkspaceSize` 与 `workspaceSize` 记录系统 workspace 与中间缓冲布局、`M/N/K` 与 `ringDepth` 便于 kernel 侧直接读取。

**Tiling 实现**：复用 `MultiCoreMatmulTiling`，A 为 GM/ND/int8、B 为 GM/NZ/int8、C 为 GM/ND/int32。NZ 分形的 N 向以 32 为最小粒度，若引擎返回的 `singleCoreN` 未对齐则按对齐值 `SetSingleShape` 重算。系统 workspace 前缀 512 对齐并保证不小于 16MB 预留区；per-token 路径额外分配 `blockNum × blockStride × sizeof(int32)` 的中间缓冲。

**Kernel 实现**：无 per-token 时，AIC 直接 `SetTensorA/SetTensorB` 后 `IterateAll` 把 INT32 结果写到 `y`；有 per-token 时，AIC 用 `Iterate` + `GetTensorC` 逐 base-tile 把 INT32 结果写入 workspace，`CrossCoreSetFlag` 通知 AIV，AIV 按子块切分 M 维，逐行 `Cast(int32→fp32)`、`Mul(scale)`、`Muls(pertoken)`、`Cast(fp32→bf16)` 后写回 `y`。

### 3.2 问题解决与优化策略

1. **遇到的问题与解决**
   - **host/device 函数标记**：辅助函数（`CeilDiv`、`AlignUpN0` 等）在 device 端 `__aicore__` 函数与 host 端 `CalcQmmTiling` 中都要调用，直接标 `__aicore__` 会报「aicore function from host function」，不标则报「host function from aicore function」。改为宏 `CEIL_DIV` / `ALIGN_UP_N0` 后两个域都可展开使用。
   - **系统 workspace 绑定（aicore timeout）**：直接下发场景首次运行即 `aicore timeout`。定位到 2201 上 `GetSysWorkSpacePtr()` 实际返回 KFC 地址（`__get_kfc_workspace_addr()`），而 `SetSysWorkspace` 已废弃、只写保留变量。改用 `SetSysWorkspaceForce`（内部 `__set_kfc_workspace_addr`）真正写入 KFC 地址后解决。
   - **`InitSocState()` 缺失**：matmul 引擎使用前需先初始化 Cube 状态（`set_mask_norm` / `set_l1_3d_size` 等），在 `REGIST_MATMUL_OBJ` 前补上 `AscendC::InitSocState()`。
   - **AIV 行步长错误（M=50,N=6144 精度失败）**：`GetTensorC(..., enSequentialWrite=true)` 时中间缓冲按「实际 tile N」紧密排布，行步长应为 `curBaseN` 而非 `baseN`。修复后 24 例全部通过。
   - **Profiler 陈旧目录误命中**：`kernel_details.csv` 按目录名降序选择时会因 PID 前缀误命中历史采集目录，清理遗留采集目录后数据正确。

2. **AI 辅助情况**：本次实践使用了 AI 工具辅助编码与调试。AI 协助完成了 Tiling/Kernel 的骨架搭建，并协助定位了上述 workspace 绑定、`InitSocState`、行步长等运行期问题。AI 给出的建议并非直接照搬，本人通过 24 例精度比对（INT32 精确匹配 + BF16 容差比对）和 Qwen3-8B 网络推理（输出语义正确、decode 耗时达标）逐项验证了正确性，确认 AI 未引入新的精度或功能问题。心得体会：AI 在提供 API 用法和排错思路上效率高，但底层算子的 host/device 边界与跨核同步仍需结合 CANN 头文件与实际运行日志独立判断。

3. **性能优化策略**：当前实现为「Cube 主算 + Vector 反量化」的基本方案，AIC 与 AIV 之间采用单标志位串行握手（AIC 全部写完后 AIV 再消费）。从 2.2 结果看，INT32 路径性能与规模成正比、表现正常；BF16 反量化在 M≥4096 的大 shape 下耗时明显偏高（如 N=24576 时约 6.9ms），瓶颈在于 AIV 逐行反量化且与 AIC 无流水重叠。后续优化方向是引入 ring buffer 让 AIC/AIV 按 base-tile 重叠执行、以及 AIV 反量化的分块向量化，从而压低 BF16 大 shape 延迟。

## 四、收获与感悟

通过本次实践，完整走通了「需求分析 → Tiling 设计 → Cube 主算 → Vector 反量化 → 单算子测试 → 模型接入」的自定义算子开发链路，对 AscendC 的 matmul 引擎、host/device 边界、系统 workspace 语义、`__mix__(1,2)` 下 AIC/AIV 跨核同步有了更深入的理解。最大的体会是：算子开发中「能编译」与「能跑对」之间隔着大量运行期细节（workspace、SocState、tiling 对齐、数据排布），需要结合精度测试和 profiler 逐项收敛；同时 AI 工具是很好的加速器，但最终正确性必须由本人通过可复现的测试来确认。
