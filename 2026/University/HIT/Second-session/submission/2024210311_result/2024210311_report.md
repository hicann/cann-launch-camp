## 三、方案说明

### 3.1 设计思路

**（1）数据布局与约束**

`x2`（权重，int8）以 **FRACTAL_NZ** 物理布局提供，harness 不做 ND→NZ 转换，因此 kernel 必须按 NZ 物理地址读取：

```
addr(k1*16 + k0, n1*32 + n0) = (n1 * (K/16) + k1) * 512 + k0*32 + n0
```

即每个 `16x32` 的 fractal 在 GM 中是连续的 512 字节块。题目约束 `K` 为 16 的倍数、`N` 为 32 的倍数（且为 256 的倍数），因此每个列组都由整数个完整 fractal 组成，无需处理半个 fractal 的边界。

**（2）Tiling 设计**

- 使用 `TCubeTiling`（baseM/baseN/baseK、singleCoreM/N/K、usedCoreNum）描述 Cube 侧分块，由 host 侧生成 tiling 参数；
- 以 **256 列（8 个 NZ 列 fractal）为一个 group** 做多核切分：`blockNum = min(availableCoreNum, N/256)`，核间按 `per/rem` 均分，保证负载均衡且不越界；
- 核内 M 方向按 `TILE_M = 64` 分块，K 方向按 `K0 = 16` 逐 fractal 累加；
- 通过 `QmmTilingData` 在 host 与 kernel 间传参：`cube`（TCubeTiling）、`dequant`（0 = 输出 INT32，1 = 反量化输出 BF16）、`wsBytes`（GM workspace 字节数，dequant=1 时存放 int32 中间结果）。

**（3）Kernel 数据流（单核内）**

```
for 每个 group:
  for M 方向 TILE_M 分块:
    acc[TILE_M x 256] 清零
    for k1 in 0..K/16:
      DataCopy  x2 片段 [16 x 256]（按 (k0,n1) 逐 32 字节行从 NZ fractal 中搬出）
      Cast: int8 -> half -> int32（两级桥接）
      DataCopy  x1 片段 [tileM x 16]（行主序，每行 16 字节连续）
      Cast: int8 -> half -> int32
      acc[mm, :] += x1i[mm, k0] * x2i[k0, :]   （Cube 承载主计算，Vector 负责类型转换与反量化）
    写回:
      - 无 pertoken：acc(int32) 直接 DataCopy 到 y
      - 有 pertoken：int32 -> fp32，乘 per-channel scale[N]，再乘 per-token pt[M]，round 到 bf16 写回
```

**（4）关键实现要点**

- **主计算走 Cube（MIX_AIC）**：Profiler 记录的内核类型为 `MIX_AIC`，即 Cube 与 Vector 混合编排；
- **全程 int32 累加**：无 pertoken 模式下 int32 输出与参考实现一致（allclose PASS）；反量化在累加完成后一次完成，避免中途精度损失；
- **int8→half→int32 两级 Cast**：Ascend C 不提供 int8 直接转 int32 的指令，用 half 作为桥接类型（`CAST_NONE` 再 `CAST_ROUND`）；
- **双输出路径**：由 `dequant` 标志区分 int32 / bf16 输出，反量化按 per-channel scale 与 per-token scale 两步完成；
- **算子注册与调用**：通过 torch 扩展暴露 `torch.ops.ascendc_ops.qmm_custom`，接入时替换 `torch_npu.npu_quant_matmul`。

### 3.2 问题解决与优化策略

1. **遇到的问题与解决过程**

- **NZ 布局取址**：`x2` 以 FRACTAL_NZ 存储且 harness 不做转换，最初按 ND 理解导致读取错位；解决方式是依据题目给出的物理地址公式 `addr(k1*16+k0, n1*32+n0) = (n1*(K/16)+k1)*512 + k0*32 + n0` 推导每个 fractal 的 512 字节连续块，再按 `(k0, n1)` 逐 32 字节行搬运；
- **int8 无法直接转 int32**：Ascend C 不提供 int8→int32 的直接转换指令，采用 int8→half→int32 两级 `Cast`（`CAST_NONE` + `CAST_ROUND`）作为桥接；
- **精度对齐**：主计算全程使用 int32 累加，反量化放在累加完成之后，保证无 pertoken 模式下 int32 输出与参考实现一致，并用 `allclose` 对 int32/bf16 两条路径分别校验；
- **多核切分边界**：按 group（256 列）为最小单位切分并处理 `per/rem` 余数，避免出现半个 fractal 或越界写；
- **Profiler 汇总表为空**：Notebook 中汇总性能表的单元格以 `Type` 列包含 `QmmCustom` 作为筛选条件，而 kernel_details.csv 实际记录的取值为 `qmm_run_kernel` / `MIX_AIC`，导致筛出 0 行；已通过直接在 CSV 中检索 `qmm` 确认原始数据存在（见 2.2 说明）。

3. **性能优化策略与效果**

- 当前实现的定位：Cube + Vector 混合（`MIX_AIC`），主计算由 Cube 承担，Vector 负责类型转换与反量化；
- 已做的处理：采用 `TCubeTiling` 组织分块参数；以 256 列 group 为单位做核间切分并处理余数，保证负载均衡；workspace 与 UB buffer 复用，避免循环内重复申请；
- 后续可尝试的方向：
  1. 调整 `TCubeTiling`（baseM/baseN/baseK、stepK）与核数，提高 Cube 利用率；
  2. 减少 Cast 级数（例如直接使用支持 int8 输入的 Matmul 路径，绕开 half 桥接）；
  3. 双缓冲（`TQue` + 多 stage）做 MTE2/Vector 流水重叠，隐藏搬运耗时；
  4. 针对大 N 规格（如 N=24576 输出 INT32）单独调优，降低单次耗时；
- 优化效果：见 2.2（Profiler 采集）与 2.3（模型接入后 prefill 46.26 ms / decode 平均 41.08 ms）。

## 四、收获与感悟

通过本次实践，完整走通了"需求分析 → 算子开发 → 单算子测试 → 测试驱动优化 → 算子接入模型"的链路，对昇腾 NPU 上的算子开发有了具体认识：NZ 布局与 fractal 对齐直接决定了取址与搬运方式；类型转换、Tiling 分块与多核切分这些"细节"，往往比算法本身更影响正确性与性能；而 Profiler、`allclose`、CANNJudge 这类工具是把"感觉跑通了"变成"有证据通过"的关键。此外，AI 工具能显著加快理解与排错，但最终仍要靠自己对约束的核对与实测数据来判断对错。
