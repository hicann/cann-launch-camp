## 三、方案说明

### 3.1 设计思路

**（1）TilingData 与 Tiling 函数**

`QmmCustomTilingData` 内含标准 `TCubeTiling`、`isPertoken`、`workspaceSize` 以及本次实现自定义的多核网格参数。`CalcQmmTiling(isPertoken, M, N, K)` 根据路径分别规划：

- **INT32 路径**：使用 `MultiCoreMatmulTiling` 生成一套库多核 tiling，`SetDim(blockDim)` + `SetSingleShape(singleM, singleN, K)` + `SetTraverse(FIRSTM)`，由库负责把 M×N 拆到各核，`SetTail` 处理尾块；`usedCoreNum` 作为 launch 的 block 数。
- **BF16（pertoken）路径**：先用自研网格规划把输出划分成“行带 × 列带”，最多用满 20 个 AIC；每种（行带高/矮 × 列带宽/窄）各生成一套单核 tiling（最多 4 套），每个 block 只负责一个矩形区域并跑一次独立单核 GEMM。

**（2）Kernel 实现与数据流**

- **INT32（Cube-only）**：`C=GM`，Matmul 直接由 Fixpipe 将 L0C 的 INT32 结果写回 `y`，省去向量的中转；按 blockIdx 计算本核的行/列起点并对 A、B、C 指针做偏移。
- **BF16（Cube + Vector）**：`C=VECIN`，`qmm_custom_kernel` 通过 `Iterate/GetTensorC` 把每个 baseM×baseN 的 INT32 块取到 UB，随后向量化反量化：
  `AscendDequant<int32→float>(…, perChannelScale)` → 逐行 `Muls(perTokenScale)` → `Cast(→BF16)` → 2D `DataCopy` 写回（按全局行 stride 处理列偏移）；输出使用 `TQue<VECOUT,2>` 双缓冲以重叠 DMA。

**（3）关键工程点**

- 每次 launch 只启动 1 个 kernel，满足平台“每用例 1 次 kernel”的要求；
- 通过 `__mix__(1,2)` 在 Cube 与 Vector 间流水，B 以 FRACTAL_NZ 读取；
- 平台/NPU 侧 KFC workspace 由 `GetLibApiWorkSpaceSize()` 申请，经 `__kfc_workspace__` 传入。

### 3.2 问题解决与优化策略

**（1）遇到的主要问题与解决**

1. **纯 Cube/纯 Vector 切分错误**：早期把大矩阵按 M 简单均分用 `IterateAll` 直写 GM，在 M=1、非整除等尾块形状上越界/结果错。最终改为 M≤64 只切 N、大 M 才二维切分，并保证每个区域形状精确、无需额外 SetTail。
2. **列切分时 INT32 输出行 stride 错误**：Fixpipe 直写 GM 时若按“区域内 N”作行 stride，列切分的结果会错位。解决：改用库多核语义（`SetDim + SetSingleShape + SetTail`），由库维护全局 C 行 stride，使 INT32 也能安全地二维切分。
3. **尾块与边界形状**：通过 100+ 组回归用例（含 M=2/3/17/33、N=5120/10240 等非 2 幂）逐一定位并修复。
4. **环境依赖**：Notebook 统一环境校验要求 numpy==1.26.4，本地先安装对齐版本后即可完整执行。

**（2）性能优化策略（测试驱动，逐轮平台验证）**

| 轮次 | 改动 | 效果 |
| --- | --- | --- |
| 基线 | 单核 all-mix（Cube+Vector 都走 VECIN/GetTensorC） | 24/24 通过 |
| 优化 1 | INT32 增大 baseN、减少 Iterate 次数 | 大 INT32 点约 −8% |
| 优化 2 | pertoken 反量化按 16 行分块、放大 baseN | 大 BF16 点约 −13% |
| 优化 3 | 多核行带并行 | 大点约 −90% |
| 优化 4 | 自研二维均衡网格（行带 × 列带） | 小/中点明显改善 |
| 优化 5 | INT32 改 Fixpipe 直写 GM | 大 INT32 再降 |
| 优化 6 | cube 行块 64→128 | 大点再降 20~30% |
| 优化 9 | INT32 改库多核调度（正确处理列切分） | 平台总和明显下降 |
| 优化 11/13/14 | host workspace 缓存、`AscendDequant`、输出双缓冲 | 稳定性提升，小幅收益 |

最终 CANNJudge 平台 24 点总和约 29.7ms，且 24/24 全通过。需要注意的是，平台单点存在 ±5% 量级的运行抖动，因此每次优化都以本地全量回归 + 平台逐点对比双重确认后再决定保留或回退。
