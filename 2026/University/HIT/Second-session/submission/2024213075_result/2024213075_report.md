### 1.3 个人开发过程说明

本次实践的目标是实现一个 A8W8 量化 MatMul 自定义算子 QmmCustom，并把它接入 Qwen3-8B 量化模型完成端到端验证。整个开发过程我按"需求理解 → Tiling 设计 → Kernel 实现 → 编译 → 单算子功能/性能测试 → 模型接入 → profiling 验证"的顺序推进。

首先是需求理解：算子输入为 INT8 的 A、B 两个矩阵与 perChannelScale，可选传入 perTokenScale；输出在无 perTokenScale 时为 INT32 精确结果，有 perTokenScale 时为反量化后的 BF16。据此我确定了双路径的设计：Cube-only 路径（isPertoken=0）与 Cube+Vector 反量化路径（isPertoken=1）。

接着是 Tiling 设计：我先约束了 N 对齐 32、K 对齐 16 的 FRACTAL_NZ 分块前提，再通过 MatmulApiTiling 计算单个 tile 的 singleCoreM/singleCoreN，把整块 M×N 切分成 mTileCount×nTileCount 的 tile 网格，最后按可用核数对 tile 做多核循环调度。Kernel 侧先实现了纯 Cube 的 INT32 路径，跑通功能后再叠加 AIV 反量化，借助 CrossCoreSetFlag/CrossCoreWaitFlag 完成 Cube 与 Vector 的核间同步与流水。

每一步我都做了独立验证：功能正确性用 INT32 的 rtol=0/atol=0 精确比对与 BF16 的 rtol=0.01/atol=0.01 比对共 12 组规格全部通过；性能用 torch_npu profiler 采集单算子 Duration；模型接入后通过 Qwen3-8B-W8A8 的 prefill/decode 分阶段 profiling 确认自定义算子已在模型中生效。

## 三、方案说明

### 3.1 设计思路

**TilingData 设计**：结构体 `QmmCustomTilingData` 以 CANN Matmul 库标准的 `TCubeTiling`（`cubeTilingData`）为核心，其中包含 baseM/baseN/baseK、singleCoreM/singleCoreN、usedCoreNum 等单 tile 分块信息。除此之外，结构体还扩展了 `isPertoken` 分支标志、原始规模 M/N/K、tile 网格计数 `mTileCount/nTileCount/totalTileCount`、多核调度核数 `cubeBlockNum`，以及 workspace 规划相关的 `systemWorkspaceSize` 与 `workspaceSize`（后者为 systemWorkspace 与 INT32 中间结果区之和）。同时保留 `matmulUsedCoreNum` 以兼容库内部 tiling 的原始核数。

**Tiling 实现**：`CalcQmmTiling` 首先用 `TORCH_CHECK` 校验 N%32==0 且 K%16==0 的对齐约束；通过 `PlatformAscendCManager` 获取核数，当 isPertoken 时核数受限为 min(AIC 核数, AIV 核数/2)（每 block 需要 1 个 AIC + 2 个 AIV）。随后用 `MatmulApiTiling` 描述单个 tile：`SetShape(min(M,128), min(N,256), K)` 限定单 tile 最大分块，`SetOrgShape(M,N,K)` 记录原始形状，`SetBias(false)` 表示无偏置，`SetBufferSpace(-1,-1,-1)` 交由库自动规划。得到单 tile 的 singleCoreM/singleCoreN 后，按 `QmmCeilDiv` 把 M、N 分别切分为 mTileCount×nTileCount 的 tile 网格，`cubeBlockNum = min(核数, 总tile数)`，Kernel 侧据此做多核循环调度。

**Kernel 双路径**：入口 `qmm_custom_kernel` 根据 `isPertoken` 分发到两条路径。

- Path1（`QmmCubeBasicKernel`，isPertoken=0）：纯 Cube 计算 INT8×INT8→INT32，结果直接写输出 GM；核内按 `tile = core; tile < totalTileCount; tile += cubeBlockNum` 的步进方式循环处理多个 tile，用 `mm_.SetOrgShape/SetSingleShape` 逐 tile 设置形状并 `IterateAll` 完成计算。
- Path2（`QmmPertokenKernel`，isPertoken=1）：Kernel 入口用 `__mix__(1,2)` 声明每 block 1 个 AIC + 2 个 AIV。AIC 复用 `QmmCubeBasicKernel` 的 Cube 计算，把 INT32 结果写入 workspace 中的中间结果区（`workSpace + systemWorkspaceSize`）；AIV 从 GM 读回 INT32，`Cast`→FLOAT32 后乘以 perChannelScale（按 N 维）与 perTokenScale（按 M 维），再 `Cast`→BF16 写回输出 GM。AIC 与 AIV 之间用 `CrossCoreSetFlag/CrossCoreWaitFlag`（QMM_CUBE_READY / QMM_VECTOR_DONE）同步，两个 AIV 按行或列对半切分同一 tile，实现 Cube 与 Vector 的协同与流水。

数据流示意：

```
INT8 A (ND, [M,K]) ──┐
                     ├──> Cube Matmul (INT8 x INT8) ──> INT32 [M,N]
INT8 B (NZ, [N,K]) ──┘                                       │
                                                             │
                isPertoken = 0：INT32 直接写输出 GM          │
                                                             │
                isPertoken = 1：                              ▼
                                   AIV 反量化：Cast INT32 -> FLOAT32
                                              Mul  perChannelScale (per N)
                                              Muls perTokenScale   (per M)
                                              Cast FLOAT32 -> BF16
                                                             │
                                                             ▼
                                                      BF16 [M,N] 输出
```

### 3.2 问题解决与优化策略

**1. 问题解决**：开发中遇到并解决了若干典型问题。一是 FRACTAL_NZ 格式的 B 矩阵分块：B 以 NZ 格式存储，其 tile 分块需满足 N 对齐 32、K 对齐 16，因此在 Tiling 阶段通过 `TORCH_CHECK(N % 32 == 0 && K % 16 == 0)` 前置校验，并对 MatmulApiTiling 返回的 singleCoreN 做 %32 校验，确保与 NZ tile 布局兼容。二是 Cube 与 Vector 的核间同步：反量化路径里 AIC 计算 INT32 与 AIV 反量化存在数据依赖，我采用 `CrossCoreSetFlag/CrossCoreWaitFlag` 的 flag 机制（QMM_CUBE_READY / QMM_VECTOR_DONE）在块间显式同步，并在 AIC 侧对未消费的 tile 做收尾等待，避免悬挂。三是 workspace 规划：将 lib workspace 与精确 [M,N] 的 INT32 中间结果区分离存放，systemWorkspaceSize 按 512 字节对齐，中间结果区紧随其后，避免库内部缓冲区与算子中间结果互相踩踏；反量化路径还额外校验 UB 是否足够容纳分块反量化所需 buffer。

**2. AI 辅助使用**：本次开发中我使用了 AI 辅助。AI 帮助我解决了不少疑惑，例如 Tiling 结构体的字段设计与 `MatmulApiTiling` 的用法（SetAType/SetBType/SetCType、SetShape/SetOrgShape、SetBufferSpace 等参数含义）、Cube 与 Vector 协同编程模型（`__mix__(1,2)` 的 block 编排与 flag 同步）、以及反量化阶段 UB 分块与 DataCopy 的 blockCount/blockLen/srcStride/dstStride 参数取值等。AI 生成的内容并非全部可直接使用，早期版本曾出现过 tile 边界与核间同步相关的问题，经我本人审查代码逻辑并配合CANNJudge的测试发现后逐步修正。对 AI 生成的内容，我的验证方式是：先读懂代码逻辑，再在CANNJudge上实际测试，随后在CANNLab的环境中，使用 .ipynb 中的单元格逐步测试： 12 组规格做功能测试（INT32 精确比对 + BF16 容差比对）、用 profiler 采集性能、最后接入 Qwen3-8B 做端到端推理验证，全部通过后才确认采纳。

**3. 性能优化策略**：结合代码实际采用的优化手段包括——多核分块并行：通过 mTileCount×nTileCount 的 tile 网格 + `cubeBlockNum` 多核循环调度，把大矩阵切分到多个核并行处理；Cube 与 Vector 核间流水：双 AIV 与 AIC 通过 flag 同步，让 Cube 计算与反量化在块间重叠，AIC 连续产出 tile 的同时 AIV 并行消费反量化；双缓冲：`QMM_BUFFER_NUM = 2` 让数据搬运与计算流水化；UB 分块反量化：`ubCalcM=16 / ubCalcN=256` 控制反量化单次 UB 占用，避免大 tile 一次搬入 UB 溢出；lib workspace 与 INT32 中间结果区分离：避免库内部缓冲区与算子中间结果冲突，保证双路径稳定运行。

## 四、收获与感悟

这次实践让我完整走通了量化 MatMul 算子从设计到上库验证的全链路。在原理层面，我深入理解了 A8W8 量化 MatMul 的核心：权重与激活以 INT8 存储、在低精度上完成矩阵乘得到 INT32 累加结果，再通过 perChannelScale（按输出列维度的缩放）与 perTokenScale（按 token 维度的缩放）反量化回浮点，兼顾了精度与算力节省。

在编程模型层面，我掌握了 Cube 与 Vector 协作的写法：Cube 负责矩阵乘这类高密度计算，Vector 负责逐元素的反量化，两者通过 `__mix__` 编排与 CrossCore flag 同步构成流水。Tiling 的多核分块思想也让我认识到，性能上限往往取决于如何在核间与 tile 间合理切分与调度。

最后，从算子开发到 PyTorch 框架接入、再到模型 profiling 验证的整个工程过程，让我体会到单算子正确不等于模型可用，端到端的功能比对与性能采集缺一不可。这次"设计—实现—验证—接入—调优"的闭环训练，对我后续做更复杂的算子和融合算子打下了扎实基础。
