## 二、结果展示

### 2.1 单算子精度比对结果

本次实验首先对实现的 `qmm_custom` A8W8 量化矩阵乘算子进行了单算子精度验证。测试同时覆盖 INT32 原始矩阵乘结果以及经过量化尺度反量化后的 BF16 输出，并选取多组 Qwen3-8B 推理过程中具有代表性的矩阵 Shape 进行验证。

部分测试规格如下：

| M | K | N | INT32 验证 | BF16 验证 |
|---:|---:|---:|:---:|:---:|
| 1 | 4096 | 4096 | PASS | PASS |
| 1 | 4096 | 6144 | PASS | PASS |
| 1 | 4096 | 24576 | PASS | PASS |
| 1 | 12288 | 4096 | PASS | PASS |

实际运行中，上述测试的 `torch.allclose` 验证均通过。说明自定义算子在 INT8 矩阵乘、INT32 累加以及 BF16 反量化输出等关键计算路径上与参考结果保持一致。

这一步对我来说比较重要，因为一开始主要关注的是算子能否编译和运行，但真正接入模型之前，仅仅“能够运行”并不能说明实现正确。通过多组 Shape 同时验证 INT32 和 BF16 两种输出，可以确认后续性能测试建立在正确计算结果的基础上。

### 2.2 单算子性能测试结果

完成精度验证后，对 `qmm_custom` 进行了多组 Shape 的性能测试。测试发现，不同 M、K、N 组合下算子的执行时间差异比较明显，这也与矩阵规模和计算量的变化相符合。

Notebook 中部分实测结果如下：

| Shape | qmm_custom 耗时（μs） | 对比算子耗时（μs） |
|---|---:|---:|
| M=4096, K=4096, N=6144 | 651.947 | 1341.033 |
| M=4096, K=4096, N=24576 | 2766.685 | 5488.110 |
| M=4096, K=12288, N=4096 | 1419.132 | 1931.041 |

从这些测试结果可以看到，在上述几个较大矩阵规格中，自定义算子的耗时均低于对比实现。例如 `M=4096, K=4096, N=6144` 时，自定义算子耗时约为 651.947 μs，而对比结果约为 1341.033 μs；在 `N=24576` 的更大输出维度下，自定义实现仍表现出了明显的性能优势。

通过这一部分实验，我也更直观地认识到算子优化并不是单纯追求某一个 Shape 的最低耗时，而需要考虑不同输入规模、核间任务划分以及硬件利用率之间的关系。

## 三、方案说明

### 3.1 设计思路

本次实验的目标是在 Ascend C 上实现能够替代 Qwen3-8B W8A8 推理中 `npu_quant_matmul` 的自定义量化矩阵乘算子。

整体实现可以分为 Tiling、Cube 矩阵乘计算、量化尺度处理以及结果输出几个部分。

首先，在 Host 侧根据输入矩阵的 M、K、N 计算 Tiling 参数，并结合可使用的计算核数量进行任务划分。由于 Qwen3-8B 的 Prefill 与 Decode 阶段具有不同的输入特征，因此不能简单使用完全固定的切分方式，需要根据实际 Shape 对计算任务进行分配。

Kernel 侧的核心计算采用 INT8 输入执行矩阵乘，并使用 INT32 作为累加结果。对于要求直接输出 INT32 的情况，可以直接输出矩阵乘结果；对于 BF16 输出，则需要进一步结合 `weight_scale` 与 `pertoken_scale` 完成反量化，将 INT32 中间结果转换为 FP32，进行尺度乘法后再转换为 BF16。

因此整个主要数据流可以概括为：

`INT8 Input × INT8 Weight → INT32 MatMul → Scale → FP32 → BF16 Output`

实现过程中还需要考虑不同 Core 对输出矩阵区域的划分，避免多个核重复处理同一区域，同时尽量保证各个核之间负载均衡。

最终将算子注册为：

`torch.ops.ascendc_ops.qmm_custom`

并在 Qwen3-8B 的 `CompressedTensorsW8A8Int8LinearMethod.apply_weights` 中替换原有 `torch_npu.npu_quant_matmul` 调用，从而完成从单算子实现到真实模型推理的完整接入。

### 3.2 问题解决与优化策略

#### 1. 实践过程中遇到的问题

这次实验中比较麻烦的部分实际上不只是算子代码本身，环境、Notebook、源码路径和模型接入都遇到了一些问题。

最开始运行 Notebook 时出现过 Jupyter Kernel 一直处于执行状态的问题。排查过程中通过 `jupyter console` 验证 Python Kernel 本身能够正常执行，之后重新确认 Jupyter Server 与 VS Code Notebook 的连接，最终恢复了 Notebook 环境。

另一个比较明显的问题是仓库路径。最开始使用的工程副本中缺少 `inference_scripts` 和部分算子编译文件，因此出现过 `ModuleNotFoundError: No module named 'inference_scripts'` 以及找不到 `CMakeLists.txt` 的问题。进一步检查目录后发现环境中存在完整的 `cann-learning-hub` 副本，切换到完整工程后，环境检查、算子编译和后续模型推理才能按照 Notebook 原有流程正常执行。

在算子实现过程中，还需要同时处理 INT32 和 BF16 两条输出路径。尤其是 BF16 路径不仅是矩阵乘，还涉及 per-channel `weight_scale` 和 per-token scale 的反量化。如果尺度对应关系或者数据类型转换存在错误，算子即使能够运行，也无法通过最终的 `allclose` 精度验证。因此调试时先保证计算正确，再进行性能测试。

#### 2. AI 辅助使用情况与体会

本次实践过程中使用了 AI 辅助进行代码阅读、错误定位以及调试思路分析，但实际修改、运行和验证仍然需要结合当前 Ascend C 环境逐步完成。

AI 对我帮助比较大的地方不是直接生成一份代码，而是在面对比较陌生的 Ascend C 工程结构时，帮助我快速理解 `TilingData`、Host 侧 Tiling、Kernel 实现、Torch 算子注册以及模型接入之间的关系。

例如在遇到 Jupyter 无法执行、`inference_scripts` 找不到、工程中缺少 `CMakeLists.txt` 等问题时，单看报错比较容易把注意力一直放在代码本身，而实际原因分别属于 Notebook 连接和仓库路径问题。AI 辅助我把这些问题逐层拆开验证，从而减少了无目的修改代码的情况。

但这次实践也让我认识到 AI 给出的修改不能直接当成最终答案。特别是在硬件算子开发中，代码是否正确最终还是要依赖编译结果、精度测试、Profiling 数据以及真实模型推理来验证。AI 更适合作为调试和理解工具，而不是替代实验验证。

#### 3. 性能优化思路

本次优化主要围绕计算任务切分、不同 Shape 的适配以及减少不必要的数据处理展开。

首先根据矩阵 Shape 和硬件 Core 数量进行任务划分，使不同计算核处理不同输出区域，尽量提升并行度并减少负载不均。

其次，对 Prefill 和 Decode 两种典型场景分别考虑。Profiling 可以看到 Prefill 中典型 M=50，而 Decode 中 M=1，两者的并行空间和计算特征并不完全相同。因此在设计 Tiling 时需要避免只针对大 M Shape 进行优化。

对于 BF16 输出路径，则将 INT32 累加结果按照量化参数完成反量化和类型转换，尽量以分段方式处理数据，避免额外的大规模中间数据搬运。

从最终性能测试来看，在部分较大 Shape 上自定义算子已经获得明显的耗时下降，但不同 Shape 的收益并不完全一致。后续如果继续优化，可以进一步针对 Decode 阶段 M=1 的场景设计专门的 Tiling 策略，并结合 Profiling 分析 Cube、Vector 和数据搬运之间是否仍存在等待或利用率不足的问题。

## 四、收获与感悟

这次实验是我第一次比较完整地接触“一个算子从实现到真正进入大模型推理”的全过程。以前学习 PyTorch 时，矩阵乘基本就是一行 `torch.matmul`，很少会继续考虑这行代码到了 NPU 上之后究竟怎样划分任务、怎样搬运数据以及怎样利用不同计算单元。

这次从 Ascend C 的 Tiling、Kernel、INT8 矩阵乘、INT32 累加、BF16 反量化，一直到编译动态库、注册 Torch 算子，再把它替换进 Qwen3-8B W8A8 的真实推理框架，我第一次比较清楚地建立了从上层 AI 模型到底层硬件算子之间的联系。

整个过程中最深的感受是，算子开发和普通 Python 编程的思维差别很大。普通程序很多时候首先关注“结果能不能算出来”，而算子开发不仅要求结果正确，还必须关注数据类型、内存、任务切分、Core 数量和不同 Shape 下的性能表现。一个实现即使能够通过编译，也离真正可用还有精度验证、性能验证和模型接入很长一段距离。

另外，这次遇到的几个问题也让我对工程调试有了更实际的认识。Jupyter 卡住时需要区分是代码问题还是 Kernel/Server 问题；模块找不到时需要检查实际工程路径，而不是马上修改 Python；算子运行成功之后还需要通过 Profiling 判断它到底有没有真正进入模型计算链路。这些排查过程虽然比单纯写代码耗时，但也是这次实验里我觉得最有价值的一部分。

最后成功看到 Qwen3-8B 使用自己接入的 `qmm_custom` 完成推理，并得到 43.88 ms 的 Decode 平均推理耗时，再看到 Profiling 中真实出现不同 Shape 的 `QmmCustom` 调用时，才真正感觉前面的实现、编译和替换形成了一个完整闭环。

通过这次实践，我对 AI 系统的理解也从单纯关注模型结构向下延伸了一层。Transformer、量化和推理框架最终都必须落到具体硬件计算上，而算子正是连接模型与硬件的重要环节。对我来说，这次实验最大的收获不只是完成一个 A8W8 MatMul，而是第一次真正理解了“大模型推理优化”在工程层面具体是在优化什么。
