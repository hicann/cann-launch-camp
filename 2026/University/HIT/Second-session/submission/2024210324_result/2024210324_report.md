## 三、方案说明

### 3.1 设计思路

**总体架构**：算子为 A8W8 量化 matmul——INT8×INT8 累加为 INT32，可选经 per-channel（`scale`）与 per-token（`pertoken`）反量化输出 BF16。采用 **Cube 主算 + Vector 反量化** 的 SIMD 架构，通过 `isPertoken` 标志分派到两条数据流不同的路径。

**TilingData 设计**：`QmmCustomTilingData` 结构如下（8 字节对齐）：

| 字段 | 说明 |
| --- | --- |
| `TCubeTiling cubeTilingData` | Cube 侧核心 tiling（含 `M/N/Ka/Kb`、`baseM/baseN/baseK`、`singleCoreM/N`、`usedCoreNum`、`iterateOrder` 等），由 host 生成、AIC/AIV 共用 |
| `isPertoken` | 路径分派标志：0 → Cube-only INT32；非 0 → Cube+Vector 反量化 |
| `workspaceSize` | 传给 kernel 的 workspace 总字节 = `sysWorkspaceSize + ringBytes` |
| `sysWorkspaceSize` | KFC 系统 workspace 前缀大小（512 对齐，≥16MB） |
| `M` / `N` / `K` | 问题规模，供 kernel 侧推导尾块与偏移 |
| `ringDepth` | ring 槽深（`QMM_RING_DEPTH=4`），AIC/AIV 共用 |
| `reserved` | 保留字段 |

**Tiling 实现（host `CalcQmmTiling`）**：取平台 AIC 核数作为 `dim`；用 `MultiCoreMatmulTiling` 设置 A=GM/ND/int8、B=GM/NZ/int8、C=GM/ND/int32，调用 `GetTiling` 生成 `cubeTilingData`；增加 **NZ 切片对齐护栏**——若 `singleCoreN % 32 != 0`，则按 `dim` 重新对齐后二次 `GetTiling`，保证 NZ 格式合法。系统 workspace 取 `max(AlignUp512(GetLibApiWorkSpaceSize()), 16MB)`（2201 的 `RESERVED_WORKSPACE` 为 16MB）作为兜底；pertoken 路径下额外计算 ring 字节 `QMM_RING_DEPTH × usedCoreNum × baseM × baseN × 4`。

**两条 Kernel 路径的数据流**：

- **Path1（`isPertoken==0`，Cube-only）**：AIC 独立完成 `int8×int8→int32` 并**直写 `y`**，AIV 直接返回空转。当 `M≥512` 且 shape 命中门控时，走 `L2CacheOptimizer` 块调度 + 编译期常量 tiling（`QmmL2cKernel`），提升大 shape 下 L2 命中与 MAC 利用率。

- **Path2（`isPertoken!=0`，Cube+Vector 融合）**：单次 `__mix__(1,2)` launch 内 AIC/AIV 协作：

```
AIM:  A(int8,ND) ┐
                 ├─► Cube(int8×int8) ──► int32 C ──► ring[slot] ──SetFlag(5)──┐
      B(int8,NZ) ┘                                                            │
                                                                              ▼
AIV:  ring[slot] ──► Cast(CAST_RINT→f32) ──► ×scale[n] ──► ×pertoken[m] ──► Cast(CAST_RINT→bf16) ──► y
       ▲                                                                      │
       └────────────────── WaitFlag(5) ◄── SetFlag(3, release) ◄──────────────┘
```

AIC 以 base-tile 为单位生产 INT32 `C` 到 ring workspace（深度 4 槽/核），每写完一槽用 `CrossCoreSetFlag<2, PIPE_FIX>(5)` 通知 AIV；AIV 用 `CrossCoreWaitFlag<2>(5)` 消费，做完反量化后用 `CrossCoreSetFlag<2, PIPE_MTE2>(3)` 释放槽位，AIC 在 ring 满时 `CrossCoreWaitFlag<2>(3)` 等待。AIC/AIV 分工由 `__mix__(1,2)`（1 AIC + 2 AIV）与 `GetSubBlockNum/GetSubBlockIdx` 确定，保证两子核按行（或单行时按列）切分。

**workspace 布局**：`[ sys 区（≥16MB） ][ ring 区 ]`。kernel 内 ring 指针 = `workspace + sysWorkspaceSize`，用显式偏移而非 `GetUserWorkspace`，确保 ring 一定落在本 tensor 内。

### 3.2 问题解决与优化策略

#### 1）关键问题与解决

- **系统 workspace 入参语义不明**：notebook 以 torch 扩展方式直调，host 未提供独立的 sys workspace 入参，而 Matmul 等高级 API 又依赖系统 workspace。解决方案是先在 2201 上做上板探针（E1）实测，观测到直调 runtime 已**自动绑定 KFC 缓冲**（`GetSysWorkSpacePtr() != workspace`），据此最终采用「sys 前置区 + ring 区」的合并布局，并在 kernel 侧以 `SetSysWorkspace` + `GetSysWorkSpacePtr()==nullptr` 时的 `SetSysWorkspaceForce` 兜底。`SetSysWorkspace` 触发 deprecated 告警，但仅为告警、不影响编译与结果。
- **cell 13 性能汇总显示为空**：定位为 `prof_output` 目录下遗留了历史采集目录，cell 13 用字符串降序挑选最新目录时被旧目录「抢命中」，导致解析到不含本轮记录的 CSV。清理遗留目录后重跑即恢复完整 12×2 表，属采集脚本/环境残留问题，非算子缺陷。
- **环境依赖不一致**：环境中的 `numpy` 版本与 `requirements` 固定版本不符，降级到 **1.26.4** 后与工程一致。

#### 2）性能优化策略

所有优化项均**不改变数值计算路径**，逐项落地并回归验证：

| 优化项 | 面向瓶颈 | 效果说明 |
| --- | --- | --- |
| per-base-tile ring 流水（`QMM_RING_DEPTH=4` + CrossCore 双向握手） | AIV 反量化藏入 Cube | Cube 生产与 Vector 反量化重叠，避免为 pertoken 路径申请 `M×N×4` 全量 workspace |
| 编译期常量 tiling（AIC） | 搬入 MTE2 feed-bound | L1 K-depth 由约 96KB 提升至约 384KB，提升大 shape 的 MAC 利用率 |
| `L2CacheOptimizer` 块调度（no-pt、`M≥512` 门控） | 搬入 GM 回读 | 优化大 shape 的 L2 数据复用与块间调度 |
| AIV 反量化行批量 + pertoken 预取（strided `DataCopy` + `Brcb` + `CHUNK_N=8192`） | AIV 搬入/标量 | 减小反量化侧的搬运与标量开销 |
| shape→dim override（`N==6144 && M≤50 → dim=16`） | 负载均衡 | 改善小 M 场景的核间负载均衡 |

**瓶颈实测结论**：大 M 区间（如 4096,4096,24576）为**计算（MAC）主导**，Cube 利用率接近饱和（约 96%–99.7%）；小 M / 宽 N 区间（如 1,4096,24576、50,4096,24576）为**搬入（MTE2 feed-bound）主导**（mte2 ratio 约 0.79–0.85）。该实测与方案的优化项预判一致。
