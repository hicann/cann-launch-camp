## 三、方案说明

### 3.1 设计思路

**（1）TilingData 设计**

`QmmCustomTilingData` 包含四类字段：

- `TCubeTiling cubeTilingData`：由 `MultiCoreMatmulTiling` 自动填充的标准 Matmul 分块参数（`baseM/baseN/baseK`、`singleCoreM/N`、`usedCoreNum` 等），Kernel 侧 `REGIST_MATMUL_OBJ` 依赖它完成内部 L0/L1 缓冲分配与遍历。
- `isPertoken` / `workspaceSize`：路径选择标志；Path2 所需的 GM workspace 字节数（`M*N*sizeof(int32)`）。
- `M/N/K`：完整矩阵逻辑维度，供 Kernel 寻址与尾块判断。
- `rowsPerCore/colsPerCore/blocksPerRow/blocksPerCol`：多核二维网格，把 `blockIdx` 唯一映射到“第 mBlock 行分块、第 nBlock 列分块”。

**（2）Tiling 策略**

- 平台核数取 `GetCoreNumAic()`；小 M（decode/prefill 短输入，M≤64）只切 N 方向，让更多核并行；大 M 时以 N 方向分块为主、剩余核再沿 M 切，并让 N 分块数尽量整除核数以避免“只用了部分核”。
- 分块对齐：单核 M 按 16 向上取整；单核 N 按 32 向上取整并满足 `baseN=256`，这是 INT8 NZ 格式列块寻址 `offsetB = nStart * K` 成立的前提。

**（3）Kernel 数据流（两条路径）**

- **Path1（INT32，Cube-only）**：`QmmCubeBasicKernel` 只在 AIC 上执行。`CalcQmmTile` 由 `blockIdx` 算出 (offsetM, offsetN, curM, curN)，`SetTensorA(x1[offsetM*K]) / SetTensorB(x2[offsetN*K]) / IterateAll(y[offsetM*N+offsetN])` 直出 INT32；同组 AIV 无任务直接返回。
- **Path2（BF16，Cube+Vector）**：AIC 先把 INT8 matmul 的 INT32 结果 `IterateAll` 写入 GM workspace 对应分片，`End()` 后通过 `CrossCoreSetFlag`（旗标 0x8/0x9）通知同组两个 AIV；AIV 等待 `CrossCoreWaitFlag` 后，两个核各处理分片一半的 M 行，对每行执行 `Cast(int32→fp32, CAST_RINT) → Mul(perChannelScale) → Muls(perTokenScale) → Cast(fp32→bf16, CAST_RINT)`，写回 `y`。
- 外层按 N 列分段把 `perChannelScale` 取到 UB 并在该段所有行间复用，减少 GM 读取；INT32 输入与 BF16 输出队列深度取 2，使 GM↔UB 搬运与 Vector 计算按行流水重叠。

**为什么这样设计**：把“Cube 写 INT32 中间结果”与“Vector 反量化”解耦到两块内存与两类核上，正好匹配 `__mix__(1,2)` 的 1 个 Cube + 2 个 Vector 协作模型；`CrossCoreSetFlag/WaitFlag` 只做“就绪通知”，不阻塞整段流水，从而让反量化与下一次 Cube 计算尽量重叠。

### 3.2 问题解决与优化策略

**（1）遇到的问题与解决**

1. **混合模式编译失败**：初版在 `lib/matmul_intf.h` 之后才定义 `ASCENDC_CUBE_ONLY`，导致 Cube/Vector 混合模型下 Matmul 接口编译报错。解决：将宏放到 `matmul_intf.h` **之前**，并理解该宏的作用是让 Matmul 在混合场景下只生成 Cube 侧实现。
2. **大 shape 结果错位**：按 ND 直觉计算 B 矩阵列偏移导致部分规格全错。解决：推导 FRACTAL_NZ 的物理排布，确认“单核 N 起始按 32 对齐时，列块起始元素偏移恰为 `nStart*K`”，并在 Tiling 侧强制 32 对齐。
3. **AIV 侧 UB 初始化冲突**：向量队列若在非 AIV 分支也 `InitBuffer`，会与 AIC 侧资源冲突。解决：只在 `ASCEND_IS_AIV` 分支初始化 vector 队列与 FP32 计算缓冲。
4. **中间结果与 Matmul 内部缓冲相互踩踏**：把 Matmul 内部系统 workspace（`GetSysWorkSpacePtr`）与 Path2 的 INT32 中间结果（用户 workspace）在内存角色上分离，避免复用同一段 GM。
5. **无法通过只读代码确认运行正确性**：最终以“编译 + 24 条单算子精度用例全通过”作为功能验收门槛，再进入模型接入。

**（2）AI 工具（CANNBot）使用情况与心得**

本次实践使用了 CANNBot（昇腾/Ascend 领域的 AI 编程助手，运行于本机 VSCode + opencode 环境）辅助开发：

- **解决的疑惑**：
  - 帮助梳理了 `MultiCoreMatmulTiling` / `TCubeTiling` 的字段含义与 `REGIST_MATMUL_OBJ` 的用法，理解“为什么先 `SetOrgShape`/`SetTensorA/B` 再 `IterateAll`”。
  - 解释 `__mix__(1,2)`、`ASCEND_IS_AIC/AIV`、`CrossCoreSetFlag/WaitFlag` 的协作语义，澄清“同组 2 个 AIV 如何分半 M 行”。
  - 协助定位 `ASCENDC_CUBE_ONLY` 宏位置、NZ 偏移等易错点，并对 TilingData/Path1/Path2 的 TODO 给出了可运行的实现草案。
  - 在本机实际执行了编译与 12 组规格 ×2 路径的精度自检，输出 PASS 结论供我核验。
- **是否引入新问题及验证方式**：AI 初稿**并不能直接代表正确**。例如它建议的通用写法必须与 8B 推理的真实 shape 对齐条件（baseN=256、N 32 对齐）相吻合，因此我逐行 review 了偏移与循环边界；编译通过 ≠ 数值正确，最终以 24 条精度用例与后续模型输出的一致性作为验证。本机出现的数值错位问题即是通过“golden 差异定位 + 对齐条件核查”发现的，并非 AI 一次给出即为正确。
- **心得**：AI 适合做“知识问答 + 首版代码 + 解释报错”，但**方案正确性的唯一依据是真实环境验证**。我会要求 AI 给出设计理由并保留手工核对关键约束（对齐、偏移、flag 同步、workspace 布局）的习惯；遇到不理解的生成代码，先让它解释再决定是否采纳。

**（3）性能优化策略与效果**

当前实现中已包含的优化（后续按 Profiler 结果继续迭代）：

- 小 M 场景只切 N 维，使 decode/prefill 的细长矩阵也能用满多核；
- Path2 两个 AIV 均分 M 行，反量化并行度 ×2；
- 按 N 列段缓存 perChannelScale，避免逐行重复读 GM；
- INT32 输入队列与 BF16 输出队列双缓冲，行间 GM 搬运与 Vector 计算流水重叠；
- （可选进一步优化）Cube 侧把 N 分成两段，段 0 完成后立即唤醒 AIV，使其与 Cube 段 1 计算重叠。

优化效果以 notebook 5.2/7.x 的 Profiler 数据为准（运行后填入 2.2/2.3），所有优化都以“精度用例全通过 + 性能提升为正”为收敛条件，避免只追求单指标。
