## 三、整体技术方案详解
### 3.1 整体设计方案
#### 3.1.1 Tiling分片结构体与多维分块策略
自定义`QmmCustomTilingData`结构体存储CANN矩阵运算库输出的`TCubeTiling`分片参数，同时记录是否开启逐token缩放、M/N/K原始维度、单核处理M/N尺寸、二维网格分块数量、Vector向量计算分片大小以及临时内存空间相关参数。
分片计算阶段通过`PlatformAscendCManager`工具类获取硬件可用AIC计算核心数量，调用`ChooseGrid`函数完成逻辑核网格分配：
1. 解码阶段或M≤64小批量场景：仅沿N维度切分数据，避免单核处理M维度数据量过小降低硬件利用率；
2. 预填充阶段或大批量M场景：同步切分M、N双维度，最大化调用硬件AIC核心并行算力；
3. M维度分片严格按16对齐；INT8 FRACTAL_NZ权重存储格式下N、K维度分片需按32对齐；
4. 同等硬件核数方案中，优先选择单核N分片长度约为单核M分片2倍的分配方式，基础分片尺寸上限设定128×256；
5. 调用`GetTiling`接口后，使用接口实际返回的单核M/N分片尺寸重新计算分块数量与全局内存地址偏移，规避硬件平台为适配L0/L1缓存约束调整分片后，全局内存地址计算错位问题。

BF16反量化运算分支：系统预留基础临时内存后，额外分配一段对齐512字节的用户临时内存，存储空间大小为`M×N×int32_t数据字节数`，用于存放矩阵乘中间INT32结果；纯INT32运算分支无需该段中间缓存。

#### 3.1.2 纯Cube计算内核（QmmCubeBasicKernel）
`QmmCubeBasicKernel`仅在AIC矩阵计算单元执行运算。每个逻辑计算核心根据二维网格编号确定当前分片M、N维度起始坐标与边界尾块长度；输入矩阵A采用ND标准存储格式，权重矩阵B采用INT8 FRACTAL_NZ压缩存储格式，计算输出C为ND格式INT32数据。内核配置全局原始维度与尾块修正参数后调用底层矩阵乘接口，运算完成后直接将结果写入全局输出内存。

#### 3.1.3 Cube+Vector混合计算内核（QmmPertokenKernel）
`QmmPertokenKernel`采用`__mix__(1, 2)`混合硬件调度策略，单个AIC矩阵单元配套2个AIV向量运算单元：
1. AIC单元完成INT8量化矩阵乘法，将INT32中间计算结果写入用户临时内存；
2. 通过`CrossCoreSetFlag`、`CrossCoreWaitFlag`多核同步接口，确保全局内存数据搬运完成后，再启动同组向量单元运算；
3. 2个AIV单元分摊当前M分片所有行数据，单次向量分片读取1024个元素，同步读取中间矩阵结果与逐通道缩放系数；
4. 依次执行INT32转FP32浮点、乘逐通道缩放系数、乘逐token缩放系数，采用就近取整模式转换为BF16格式，最终写回全局输出内存。

#### 3.1.4 Torch上层接口与大模型适配流程
主机侧接口优先校验硬件设备、张量维度、数据类型、M/N/K数值、缩放系数数组长度与FRACTAL_NZ存储对齐限制，根据是否传入`perTokenScale`缩放参数自动切换INT32或BF16输出分支。借助`TORCH_LIBRARY`、`TORCH_LIBRARY_IMPL`宏完成`qmm_custom`算子注册，编译生成动态库`libascendc_ops.so`。
大模型适配阶段：在量化推理模块导入代码中主动执行`torch.ops.load_library(...)`加载算子动态库，随后将原量化矩阵乘调用语句替换为自研`torch.ops.ascendc_ops.qmm_custom(...)`接口。

### 3.2 开发问题排查与性能优化手段
1. **工程文件路径不统一**
本地Notebook运行环境的文件挂载路径与CANNLab平台目录存在差异。团队修改工程定位逻辑，统一基于代码仓库根目录与固定路径`/mnt/workspace/gitCode/cann/cann-learning-hub`定位文件，运行脚本前提前校验模型权重、配置YAML、算子动态库、推理脚本文件是否存在。

2. **量化大模型权重缺失**
初期组员本地环境无Qwen3-8B-W8A8量化权重文件。团队先按照第五章教程使用AMCT工具完成W8A8模型量化导出，校验`config.json`配置文件与权重文件夹完整后，再执行第六章推理脚本。

3. **推理子进程无法识别自定义算子**
初次仅替换Python顶层调用代码，推理脚本运行时报`ascendc_ops`不存在`qmm_custom`属性。根因是Notebook主进程加载算子动态库，但`infer.sh`脚本新建独立Python子进程，未重复加载库文件。修复方案：在量化模块导入阶段增加动态库加载代码，重新执行推理脚本，确认程序返回码为0无报错。

4. **依赖工具链版本冲突**
安装AMCT量化工具时，自动将Torch、Torch-NPU版本降级至2.7.1。团队按照第六章标准依赖环境，重新安装Torch 2.8.0、Torch-NPU 2.8.0.post4，导入框架校验版本无误后重新编译算子代码。

5. **性能采样CSV表格无有效数据**
Profiler输出表格中`Input Shapes`、`Output Data Types`字段存在空值，原始分组统计逻辑会直接丢弃对应记录。团队新增「算子名称+硬件类型」双条件过滤逻辑，填充缺失字段默认值并统一数值格式，最终正常统计出Prefill、Decode阶段完整耗时数据。

6. **算子性能优化措施**
小批量M场景仅切N维度、大批量M场景采用M/N二维并行分块；设置128×256分级基础分片；采用Tiling接口返回真实分片尺寸计算内存偏移规避地址错误；BF16反量化分支分配双向量单元分摊计算行、拆分向量分片提升流水线执行效率。多重优化兼顾解码阶段低延迟、预填充阶段高并行度、FRACTAL_NZ权重内存地址正确性与向量单元流水吞吐性能。

7. **CANNJudge平台工具链版本兼容问题**
本地Notebook基于CANN 8.5.2可24组用例全量通过；迁移至CANN 9.0.0标准算子工程后，编译流程与全部INT32用例正常运行，但部分BF16混合运算用例出现数值偏差或多核同步等待超时。团队依据平台报错日志，尝试调整向量计算流水线屏障、混合硬件单元映射规则、双向多核同步逻辑等兼容方案，平台评测结果仍为17/24通过，相关兼容问题记录为后续迭代优化方向。

### 3.3 AI辅助工具使用说明
项目开发期间借助AI工具辅助分析环境路径配置、Notebook运行报错日志、子进程动态库加载逻辑、性能采样CSV字段解析，同时协助整理测试数据与报告整体框架。
AI初次给出的大模型算子替换方案仅修改顶层函数调用，未考虑`infer.sh`会创建独立Python子进程，导致出现动态库未注册故障。团队未直接照搬AI生成方案，根据`AttributeError`报错定位进程隔离问题，补充子进程内部加载动态库代码；并通过「重启Notebook内核—完整执行全部13段代码—校验24项精度结果、模型文本输出、性能采样表格」整套流程验证修复效果。
本次开发经验证明：AI工具可快速辅助定位问题、生成备选解决方案，但昇腾硬件底层算子开发、框架依赖版本管理、多进程资源隔离等场景，必须依托NPU硬件实测结果验证方案有效性。
